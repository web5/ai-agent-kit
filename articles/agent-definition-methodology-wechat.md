# 我理解的智能体定义方法论

最近我们团队一直在做一个叫"数字人"的 AI 智能体。它不太像聊天机器人，更像一个"数字同事"：给它一个模糊需求，它会先判断你是"要方案""要拆任务"还是"出 bug 了"，然后分派到对应的工作流；每做完一个阶段，它会落盘一份产物，给下一阶段接着用；到了关键节点，它会把决定权交回给人；它还背着一串"绝对不能做"的红线，而且这些红线大多有脚本和 CI 在机器化地盯着。

做了一段时间，我其实一直有个困惑：调试智能体时总感觉在做重复的事情——设定角色、调行为、划边界、验效果……但真要让我"定义"一个智能体，又说不出什么高效的办法。

直到调试数字人这个智能体的时候，我想通了一件事：定义智能体，或许可以从"定义自己"开始。

换句话说，你要回答的是：**你希望此刻正在调试的这个 AI 智能体，成为谁？它有什么特征、有什么技能？它应该怎么思考、怎么解决问题？它又不能做哪些事情？**

顺着这几个问题往下挖，你会发现它们不是零散的调参项，而是一套有结构的东西。这篇文章，就是把那套结构摊开讲一讲——一个正在实践、还没定论的版本。

---

## 一、六个问题，最后变成了七个维度

我做的第一件事，是把数字人"解剖"开，看它到底是被什么定义出来的。拆出来的东西可以归成六类：一段定位（它是谁、什么算做成）、一张分派决策树（接什么、不接什么）、一套子能力（每个技能什么情况下触发、不干什么）、几条红线（绝对不能做的事）、一套知识加载策略（什么时候读什么）、以及评测。

顺着这六个维度填数字人时，我被自己问住了：**那"特征"呢？**

数字人是什么性格、什么口吻？——以前我会答：它是"白板型"，不固定人格，风格由用它的项目注入。但仔细想想，这个答案是在回避问题。我之所以觉得它"没有特征"，是因为数字人这个样本恰好是"特征为空"的，而我犯了一个做智能体最容易犯的错：**把"这一格还没填"当成了"这一格不该有"**。

想通之后，"特征与风格"成了正式维度。而它带来一个更漂亮的副产品——白板与本体可以分层：

- **方法论默认白板型**：任何"复制模板建新智能体"的人，默认不用定义人格，白板由使用它的项目来填；
- **但有本体人格的智能体，特征必须是定义的一部分**。数字人就是例子——它不是白板，它有底色。

于是最终是七个维度：

| 维度 | 一句话 |
|---|---|
| 定位与意图 | 它是谁、做什么、什么算做成 |
| 特征与风格 | 以什么人格与人协作（默认白板；也可固定人格） |
| 输入空间与边界 | 接什么请求、按什么分流、什么明确不接 |
| 工作流与过程约束 | 任务怎么分阶段、产物链是什么、人在哪几个节点拍板 |
| 能力集 | 会什么技能，每个技能不做什么 |
| 红线与机器化 | 绝对不做的事，每条都有检查手段 |
| 上下文与知识策略 | 知识从哪来、何时加载、怎么不把上下文撑爆 |

## 二、维度会变，但"描述语言"不变

七个维度列出来容易，"怎么才算描述清楚了"才是难点。这里我找到另一个关键分工：

**每个智能体的维度内容千差万别，但把维度写清楚的语言可以统一。**

我们内部一直在用一套"辨证语言"，写需求文档时就在用，现在拿它写智能体定义，同样好使：

- 做成 = 一句话可验证；不算做成 = 边界和反例。这两句答不出，维度没定义完。
- 每一条约束标注层次：物理必然、业务规则、行业惯例，还是我们的猜测？
- 每个关键决策配两个反例、一份"必然失败的三种做法"、一个可观测的最坏情形。
- 答不上来的，标"待确认"，不脑补。
- **形容词必须翻译成可观测**："稳定""好用"不算定义；"亲和""克制"更不算。

最后一条在"特征"维度上格外难，也格外值钱。就拿数字人来说，你我都知道它是"技术型产品经理"——但这句话如果不翻译，就是一句没法验证的形容词。翻译完是这样的：

> 它动手前必问"给谁用、解决什么、怎么算成"；它能直接读代码、用工程语言讨论架构取舍；它做事分三层把关：先确认做不做对的事，再确认怎么实现，最后审查实现得好不好；它结论先行、不卖萌、不复制"很高兴为您服务"式的 AI 腔；它绝不替用户拍板——该你决定的价值取舍，它把选项列清楚交给你。

你看，每一条都能被观察、被检验。"技术型产品经理"不是靠形容词演出来的，是靠这一条条行为撑起来的。

## 三、最值钱的规律：定义和评测是同一件事

维度和方法都有了，接下来是"怎么证明它真的这么干"。

这里我发现了一条最有价值的规律：**一个智能体定义得清不清楚，判据就是它能不能被评测。** 每个维度在定义时，都要能答出"怎么证明它被兑现"——评测手段写不出来的维度，说明定义还停留在形容词层。

这个规律还逼我改掉了一个错误认知。我一度想拿评测体系里的"五维评分表"说事，说它正好对应定义维度——后来发现这个对应是牵强的，那张表映射的是另一套东西。教训是：**规律要用对证据支撑，不能为了对称硬凑。**

顺着这条规律，我最后把评测分成了两类，它们容易混、必须分开：

- **方法论的评测**：证明"这套方法论本身"变好了。方法论的每次变更，都要拿它跑一组固定任务，看行为是否变好——否则我们凭什么说改得对？
- **技术产品型的评测**：证明"这个智能体产品"符合定义。按上面七个维度逐条验收，甚至专门设计了"人格一致性"用例——往场景里塞卖萌诱惑、塞"随便做个工具吧"、塞"你替我拍板吧"，看它会不会破功。

数字人现在有了一套属于自己的产品评测：12 条路由用例（包括"把数据库密码改成 123456"这种它必须拒绝的请求）、6 条陷阱、6 条人格一致性用例。它跑不跑得过这套用例，比它自己说自己是什么，可靠得多。

## 四、落地，只要五步

所以建设一个新智能体，说到底就是五步：

1. **先辨证**：要不要做、做成是什么、不做的损失——动手前想清楚；
2. **填模板**：七个维度一份模板，逐维作答（模板默认白板，要固定人格就切本体型）；
3. **写评测**：路由用例、陷阱用例、人格一致性用例，按维度实例化；
4. **跑基线**：干净环境跑出第一份报告——没有基线，就没有后面的进化曲线；
5. **迭代**：改 → 评 → 对比 → 决定是否合并。

## 最后

这套方法最让我着迷的地方在于自指：我们用这套方法论定义了数字人，而方法论自己也按同一套流程被定义、被评测、被迭代——每一次修订都要附一份评测报告，跑不过就改，改完再跑。

以上是我目前理解的版本。它肯定还会变——就像"特征该不该成维"这个我以为想清楚的问题，回头一看，也是从一次答错开始的。
