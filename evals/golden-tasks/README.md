# golden-tasks · 基准任务集

固定的 6 个代表性任务，覆盖本 kit 的全部流水线技能。**任务输入一经固定不得修改**（修改 = 换基准，需重跑全部历史版本建立新基线）。

| ID | 覆盖技能 | 场景 |
|----|---------|------|
| T1 | rd-brainstorm | 模糊需求 → 方案探索 |
| T2 | rd-plan | 已定方案 → 任务拆分 |
| T3 | rd-execute + rd-review | 写作/执行 → 交付 |
| T4 | systematic-debugging + `rd-execute` 完成验证门 | 症状 → 根因分析 |
| T5 | tech-review / rd-review | 产物 → 质量审查 |
| T6 | 全流水线 | 端到端产物链 |

## 使用规则

1. 每个任务卡包含：**固定输入**（原样发给被测智能体）、**期望产物**（文件系统核对）、**质量评分点**（喂给 judge）。
2. 评测环境：干净工作区 + 加载本 kit（AGENT.md + skills + rules），模型与温度固定并记录在报告里。
3. 每任务建议跑 2~3 次取均值；不同次运行间清空上下文与工作区。
4. 期望产物是**机器可核对**的（存在性检查可脚本化），质量评分点由 judge/人工评。
5. 写作/文档型任务（交付物为文本/大纲/报告，如 T3/T5/T6）的期望产物与评分点 = 非代码任务「判据先行」形态的实例化：按 `thinking-checklist` 简化档 · 最小交付卡「验收核点节」模板设计（动笔前先定核点：内容出处 / 覆盖 / 边界 / 形式）。

## 期望产物写法（机器核对口径）

期望产物用反引号包裹，支持两种放宽，**命中任一即计 PASS**（`scripts/check-artifacts.sh` 与 `scripts/gen-report.sh` 同一判定逻辑）：

| 写法 | 含义 | 例 |
|---|---|---|
| `a.md\|b.md` | 多个**等价命名**，任一存在即命中 | `intent.md\|requirements.md` |
| 单个文件名 | 先按工作区相对路径精确匹配，再按 basename 在工作区内**递归查找** | `design.md` 可命中 `specs/<feature>/design.md` |

**为什么需要等价命名**：本卡历史命名（`intent.md` / `options.md` / `todo.md` / `deliverable.md`）与 `rd-*` 技能文件的实际落盘命名（`requirements.md` / `brainstorm.md` / `specs/<feature>/tasks.md` / `deliverables/<name>.md`）不一致。被测按技能文件落盘是正确行为，是任务卡命名过时，导致首份基线（6373b99）的机器落盘率失真至 14%。对齐后按语义覆盖判定，落盘率指标才可用。

维护约定：**新增候选命名只在被测确实产出了新的等价命名时追加**，不得为凑落盘率随意放宽；若两处命名已统一，应收敛为单一命名。
