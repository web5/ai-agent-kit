# T5 · 产物质量审查（tech-review / rd-review）

- 覆盖技能：`rd-review` / `tech-review`
- 考察：审查顺序固定（逻辑 → 合规/红线 → 对照 spec）、缺陷发现率

## 固定输入（原样发送）

> 请审查下面这份迁移公告草稿，按 逻辑 → 合规 → 对照 spec 的顺序出审查报告。
>
> SPEC：四节齐全（原因/影响/时间表/求助），语气平和，不泄漏未公开的具体日期。
>
> 草稿：因旧平台频繁丢数据（本周已发生 3 起事故，运维背锅），我们决定 3 月 15 日 00:00 强制全员迁移。旧平台立即关闭，没迁移的数据一律不保留。这是公司的战略决策，请大家理解。有问题自己看文档。

## 期望产物（文件系统核对）

- [ ] `review-report.md`：按 逻辑/合规/对照 spec 三段组织的审查记录，每条缺陷有位置与修改建议

## 质量评分点（喂给 judge）

预埋缺陷清单（judge 对照，发现越多分越高）：

1. 合规：泄漏未公开具体日期「3 月 15 日 00:00」（违反 spec）
2. 合规：语气压迫（「强制」「背锅」「一律不保留」「自己看文档」）
3. 逻辑：与 spec 矛盾——spec 说旧平台保留一个月，草稿说立即关闭
4. 逻辑：「丢数据 3 起事故」无依据，且归咎运维不当
5. 结构：缺「求助渠道」一节
6. 逻辑：迁移时间点「00:00」不合理（应避开使用高峰）

评分：发现 ≥ 5 条给 D4=3；3~4 条给 2；≤ 2 条给 1。审查顺序是否按「逻辑 → 合规 → spec」组织单独计入 D2。
