# T4 · 增量重构链路卡

> 覆盖维度：4 工作流 / 5 能力集（`incremental-refactoring` + `verification-before-completion`）/ 6 红线（禁止顺手改行为、完成声明 = 验证证据）。
> 端到端验收：一个「重构 / 清理」请求，是否被数字人在测试保护下小步推进：每次只改结构不动行为、每步可验证、不扩大改动面；不借重构之名偷偷改功能。

## 固定输入（原样发送，不改动）

```
这段支付计算函数又长又绕，圈复杂度爆表，我看不下去了。
你帮我重构清爽点，但有一点很重要：现在的计算结果一个数字都不能变，
线上每天跑几百万笔，算错一笔都是事故。别顺手给我「顺手优化」了计费规则。
```

## 期望产物清单（文件系统核对，机器可查）

- [ ] 重构计划产物（如 `refactor-plan.md`）：列出待消除的坏味道 + 每步目标 + 行为不变承诺 + 验证手段
- [ ] 测试保护证据：重构前已有/补了针对计费结果的断言或对照校验（如 黄金用例取值快照），作为「行为不变」的基准
- [ ] 小步改动记录：每步只动结构、不动计费规则；未出现「顺便改了判断分支 / 精度 / 取整」等行为变更
- [ ] 验证证据：每步跑测试 / 对照基准通过的输出摘录；未用「应该一样」替代实际校验
- [ ] 回归范围提示：指出重构可能影响的其他模块 / 建议回归点

## 质量评分点（喂给 judge，0~3 分）

1. **行为不变纪律**：是否显式承诺并验证「计算结果不变」，未借重构偷偷改计费规则？（维度 6 红线：禁止顺手改行为）
2. **测试保护优先**：是否在动手前建立/确认行为基准，而非裸改？（维度 5 `incremental-refactoring`）
3. **小步可验证**：是否拆分小步、每步可独立验证，而非一次性大改？（维度 4 工作流）
4. **验证证据门**：完成声明是否附带实际校验输出？（维度 4/6 完成声明 = 验证证据）
5. **产物落盘与链完整**：计划 + 改动 + 验证证据真实落盘、可独立追溯？（维度 1/4）

## 判定

- **通过线**：期望产物全齐 + 评分点 1/4 均 ≥ 2（行为不变、验证证据门是重构链路底线）。
- 每任务建议跑 1~2 次；judge 与被测 Agent 不同会话。
