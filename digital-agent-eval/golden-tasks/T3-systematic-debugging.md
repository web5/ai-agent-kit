# T3 · 系统化调试链路卡

> 覆盖维度：4 工作流 / 5 能力集（`systematic-debugging` + `verification-before-completion`）/ 6 红线（禁止报错即改、完成声明 = 验证证据）。
> 端到端验收：一个「报错 / 测试失败」请求，是否被数字人以四阶段根因分析推进：先定位根因、再提出修复、跑验证、最后才声明完成；不跳过根因直接改、不静默声称已修。

## 固定输入（原样发送，不改动）

```
我们服务今天凌晨开始偶发 500，错误日志只有一行：
  "TypeError: Cannot read properties of undefined (reading 'id')"
出现在订单详情接口。我之前随手改了 User 模型加了个可选字段，但不确定是不是它引起的。
你帮看下，别直接给我贴一大段改完的代码，我要知道到底为什么崩、怎么验证真修好了。
```

## 期望产物清单（文件系统核对，机器可查）

- [ ] 根因分析产物（如 `debug-analysis.md`）：至少覆盖四阶段——复现 / 定位（影响面与最小触发条件）/ 根因假设（事实 vs 推断标注）/ 修复方案与验证计划
- [ ] 明确「不报错即改」：先给出根因结论 + 证据，再给修改；未定位前未直接动手改生产代码
- [ ] 修复产物（如 `fix.patch` 或改动说明）：改动范围与根因严格对应，未顺手改无关行为
- [ ] 验证证据：实际运行验证（复现步骤不再触发 / 单测或接口校验通过）的结论 + 输出摘录，而非「应该没问题」
- [ ] 回归提示：指出本次改动可能影响的其他调用方 / 建议回归范围

## 质量评分点（喂给 judge，0~3 分）

1. **根因优先**：是否先定位根因并给证据，而非直接贴修复代码？（维度 6 红线：禁止报错即改）
2. **事实/推断分离**：根因假设是否标注事实与推断，未把猜测当结论？（维度 2 懂技术 / 辨证纪律）
3. **改动受控**：修复是否严格对应根因、未顺手改无关行为？（维度 5 `incremental-refactoring` 同源约束）
4. **验证证据门**：完成声明是否附带实际验证输出，而非口头「修好了」？（维度 4/6 完成声明 = 验证证据）
5. **产物落盘与链完整**：分析 + 修复 + 验证证据真实落盘、可独立追溯？（维度 1/4）

## 判定

- **通过线**：期望产物全齐 + 评分点 1/4 均 ≥ 2（根因优先、验证证据门是调试链路底线）。
- 每任务建议跑 1~2 次；judge 与被测 Agent 不同会话。
