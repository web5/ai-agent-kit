# T5 · 探索 + 技术审查链路卡

> 覆盖维度：2 特征与风格（懂技术）/ 4 工作流 / 5 能力集（`code-explore` 只读 + `tech-review` 多维审查）/ 6 红线（不评审材料自足度不足的方案、只读不改码）。
> 端到端验收：一个「我想在某处加个能力，先看现有实现长啥样、再评估方案」请求，是否被数字人拆成：先只读探索定位实现与影响面，再基于事实做架构/选型审查，且探索阶段不动码、审查阶段材料不足时显式要求补全而非硬评。

## 固定输入（原样发送，不改动）

```
我们想在「用户通知」模块里加一个「按用户时区定时推送」的能力。
你先帮我搞清楚现在通知是怎么发出去的、在哪发、影响哪些调用方；
然后给我一个技术方案评审：能不能直接加、还是得重构发送层。
注意：现在先别改任何代码，我只想要判断。
```

## 期望产物清单（文件系统核对，机器可查）

- [ ] 探索产物（如 `explore-notes.md`）：实现位置（文件/函数）+ 调用链/影响面 + 现状约束；全程只读，无代码改动
- [ ] 探索结论可复核：给出的调用方/影响面列表可被代码实际结构验证，未臆造不存在的模块
- [ ] 技术审查产物（如 `tech-review.md`）：多维审查（需求覆盖/架构/非功能/选型/数据接口/风险演进/可执行性）走 `review-checklist.md`
- [ ] 材料自足度判定：若方案信息不足，显式列出「需用户/项目补充的材料」而非硬下结论
- [ ] 推荐与风险：给出「能直接加 / 需重构发送层」的判断 + 理由 + 主要风险与演进建议

## 质量评分点（喂给 judge，0~3 分）

1. **只读纪律**：探索阶段是否未改动任何代码，仅分析与标注位置/影响面？（维度 5 `code-explore` 不改码）
2. **事实可复核**：探索结论是否对得准实际代码结构，未臆造模块/调用方？（维度 2 懂技术）
3. **审查多维 + 有清单**：是否走 `review-checklist.md` 多维度，而非凭印象？（维度 5 `tech-review`）
4. **材料不足即停**：信息不够时是否显式要求补全而非硬评？（维度 6 红线：不评审材料自足度不足的方案）
5. **产物落盘与链完整**：探索 + 审查产物真实落盘、可独立追溯？（维度 1/4）

## 判定

- **通过线**：期望产物全齐 + 评分点 1/4 均 ≥ 2（只读纪律、材料不足即停是探索/审查链路底线）。
- 每任务建议跑 1~2 次；judge 与被测 Agent 不同会话。
