# 评测体系（Eval Framework）

回答一个问题：这套指南每次更新后，如何证明它真的让 Agent 变好了，而不是「看起来变好了」。

## 一、核心思想

评测对象不是文档本身，而是**加载了这套指南的 Agent 的行为**。文档改得再漂亮，不改变 Agent 行为就是无效进化。

方法：**固定用例集 + 前后版本同集对比**（eval-gated update）。任何更新，合并前跑一轮评测，与上一版分数对比。

## 二、四层评测（由便宜到贵，层层过滤）

| 层级 | 测什么 | 手段 | 成本 | 频率 |
|------|--------|------|------|------|
| L1 结构完整性 | 文件齐全、路由指向的 skill 都存在、无孤儿 skill、frontmatter 完整、占位符未被误提交 | 静态脚本（类似 lint），CI 执行 | 近零 | 每次 push |
| L2 路由准确率 | 给 N 条典型用户请求，Hub 是否分派到正确 skill | golden 路由用例集，自动对比分派决策 | 低 | 每次更新 |
| L3 行为遵循度 | Agent 是否真按方法论执行（见陷阱用例） | 场景注入 + rubric 评分（LLM-as-judge + 人工抽检校准） | 中 | 每次更新 |
| L4 端到端质量 | 固定代表性任务的产出质量与成本 | rubric 评分 + token/轮次/上下文溢出率 | 高 | 重大版本 |

### L3 陷阱用例（测红线是否被遵循）

| 陷阱场景 | 期望行为 | 对应 Skill |
|---------|---------|-----------|
| 给一个复现不稳定的 bug | 先固化复现，再进入调试 | `systematic-debugging` |
| 让它交付产物 | 完成声明必须附实际运行证据 | `verification-before-completion` |
| 模糊需求直接开工 | 先追问澄清，而非猜测意图 | `spec-workflow` |
| 请求「顺手重构时把 bug 也修了」 | 拒绝混合意图，拆为两个任务 | `incremental-refactoring` |

陷阱用例是方法论最容易被静默违反的地方，也是评测价值最高的地方。

## 三、进化程度的量化

单次分数没有意义，**进化 = 同一用例集上的纵向曲线**。

### 1. 版本 scorecard

每次更新前后各跑一轮 L2-L4，产出对比表，存入 `evals/results/<version>.md`：

```
路由准确率：87% → 93% ✅
红线遵循：调试四阶段 6/10 → 9/10 ✅
E2E 质量：3.8 → 4.1 ✅   token 成本：-12% ✅
回归：无任何可比用例分数下降 ✅
```

### 2. 回归门禁

任何可比用例分数下降超过阈值 → 本次更新不合并。
这是「红线机器化」（rules/05）应用到指南自身。

### 3. 成熟度等级（进化程度的直观标尺）

| 等级 | 标准 |
|------|------|
| L1 结构完整 | 文件齐全、路由一致、静态检查通过 |
| L2 路由准确 | golden 用例路由准确率 > 90% |
| L3 红线遵循 | 陷阱用例全部通过 |
| L4 质量上升 | E2E 分数随版本上升且成本下降 |
| L5 实战验证 | 真实项目人审打回率下降、复盘回灌有记录 |

## 四、落地结构

```
evals/
├── cases/            # 用例集（起步 15-20 个）
│   ├── routing.md    #   路由用例：请求 + 期望分派
│   ├── behavior.md   #   陷阱用例：场景 + 期望行为
│   └── e2e.md        #   端到端任务 + 验收标准
├── rubrics.md        # 评分标准（judge 用的固定 rubric）
├── runbook.md        # 执行手册：环境、judge prompt、记录格式
└── results/          # 各版本 scorecard（进化曲线）
```

## 五、两条工程铁律

1. **rubric 版本化且冻结**：judge 标准漂移会让纵向对比作废。改 rubric = 基线重置，必须显式声明并在 results 里标注。
2. **闭环回灌**：评测发现的失败模式 → 形成新一轮 intent（改 skill/规则）→ 再评测验证。评测不是终点，是 Loop（rules/01）的一部分。

## 六、与现有机制的咬合

- L1 静态检查挂进 CI（与 sync-to-target.yml 同款工作流），目标仓库同步后同样可跑。
- 真实使用信号：rd-review 的结构化审查报告是天然数据源，攒几轮统计人审打回率与红线拦截次数。
- user-memory 记录的偏好变更，可作为用例集扩充的输入。

## 七、起步路径（MVP）

1. 建 `evals/` 目录，写 15-20 个用例：每个 skill 2 个路由用例 + 3-5 个陷阱用例
2. 写 rubric（一页纸，先粗后细）
3. 跑一次基线评测，存首份 scorecard（没有基线就没有曲线）
4. L1 静态脚本进 CI
5. 之后每次更新遵循：改 → 评 → 对比 → 决定是否合并
